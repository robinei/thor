## 1. Architecture and design

Overall: the shape is right for this device. One pure state (`clamshell-core`) fed by events and
answering with effects, worker threads in `clamshell-system`, an immediate-mode CPU-drawn UI, and SQLite
for everything persisted. The boundaries are real: core has no I/O and only depends on `library` +
serde; system does not depend on ui; the binary wires them. The docs describe behaviour that the code
actually implements (I cross-checked process-control.md, runners.md, files-tab.md, android.md against
running.rs/background.rs/launcher.rs/units.rs/files.rs). Tests are behaviour-level and readable. The
findings below are about where six days of fast growth have left seams.

### 1.1 `State::apply` is a fixed pipeline of `follow_*` passes with ordering dependencies (verified) — the main maintainability risk
`crates/core/src/lib.rs:304-327`: after each event, `follow_bottom_dim → follow_shown → follow_browse →
follow_idle → follow_watch → follow_program → follow_pad_mouse → follow_keymap → reconcile_pad`. On top
of that, individual event arms call more: `Event::Windows` (lib.rs:380-394) runs `follow_windows →
follow_window_rules → follow_background → show_pending → show_reopened → follow_quitting → follow_closed
→ follow_dock`, and `Event::Units`, `Event::Tray`, `Event::Game`, `tick` each run their own subsets.
There are 24 `follow_*` functions in core (grep). The order matters (e.g. `follow_windows` must precede
`follow_background` because the latter reads `r.seen`; `follow_quitting` must run after `follow_ours`
because it checks `running(game).is_some()`), but nothing states or checks it; a new feature has to be
slotted into the right arm by reading all of them.
Why it matters: this is where regressions will come from as more "after any change" rules land (there
were ~10 such commits in the last two days).
Recommendation (medium): one `reconcile()` that runs the full window/unit/background/quitting/dock chain
unconditionally after every event (it is cheap: a few dozen entries), with the per-event arms reduced to
"update the raw input". `Dirty` is already coarse (`Windows` → `BOTH`), so nothing is lost. Then
`follow_*` become private steps of one function whose order is written once. Add a test that applies the
same event sequence in different interleavings and asserts the same `running`/dock/effects.

### 1.2 `Running` encodes a state machine in field combinations (verified)
`crates/core/src/running.rs:62-83`: `origin: Origin`, plus `app_id`, `pid`, `tray`, `launches`, `seen`,
`entry` — the valid combinations depend on `origin` (Found uses pid/tray; Windows uses since/until +
seen; Ours uses launches). It is built at six sites with different combos: running.rs:225, :300, :334,
:460; found.rs:70; tray.rs:110 (plus a test helper in bottom_screen.rs:301). `follow_units`
(running.rs:431-443) mutates `origin`, `pid` and `app_id` to "promote" a Found entry.
`Session::quitting` is a `Vec<(Arc<str>, bool, Option<Effect>)>` tuple (session.rs:37).
Recommendation (medium): make `Origin` carry its data — `Ours { launches, app_id }`, `Found { pid:
Option<u32>, tray: Option<Arc<str>>, app_id }`, `Windows { since, until, app_id }` — and give `Running`
two constructors (`launched`, `found`). Replace the quitting tuple with a small struct. This removes a
class of "which fields are meaningful now" bugs and makes the tests in running.rs/found.rs/tray.rs
shorter.

### 1.3 Settings are untyped `u16`s with magic values (verified)
`crates/core/src/settings.rs`: every setting is a `u16` and the meaning of values is spread over
`choices()`, `describe()`, `impact()` and the call sites: `background.rs:128 setting == 1`, `:143
setting == 2`, `panel.rs:170 get(Setting::BottomScreen) == 1`, `lib.rs:345 get(Setting::PadMouse) ==
1`, and the sentinel `GAMES_PAUSED = 3` (settings.rs:56) resolved in `panel.rs:57 background_of`.
Recommendation (small): typed accessors on `Values` (`fn background(&self) -> Background { Runs, Pauses,
Quits, PausesGames }`, `fn bottom_dark(&self) -> bool`, …) so the number lives in one place. The storage
format can stay numeric (unreleased, no migration concerns).

### 1.4 Threading/worker model is good; D-Bus connections and process spawns are scattered (verified)
`worker.rs` (`Worker`, `Bell`, `Service`/`supervise`, `Changed`, `coalesce`) is a clean, tested pattern
and most threads use it. But: `zbus::blocking::Connection::session()` is opened fresh in
`units::connect`, `units::adopt`, `units::thaw_slice`, every `units::freeze` thread, `tray::connect`,
`device::notify`, and `battery`; the process-control doc itself measured ~8 wakeups/s from zbus executor
threads. Each blocking connection spins its own executor (inferred from zbus's design; verify with `ps
-T`). Also `Connection::new("systemd-run")` appears 7 times and `systemctl` 6 times across job.rs,
launcher.rs (`end_run` shells `systemctl stop/kill`), archives.rs, while units.rs already has a
`ManagerProxy` with `stop_unit`, `freeze_unit`, `start_transient_unit`.
Recommendation (medium): one `systemd` module owning a single long-lived session connection (`dbus.rs`
already has `Kept`/`default_proxy` helpers) and all unit operations (stop, kill, freeze, thaw, attach,
start-transient, list, wait). `launcher::end_run/adopt` and `archives::mount` become callers of it. Fewer
executors, fewer forks, one error type.

### 1.5 Effects carried out by the UI crate (verified, acceptable, note it)
`crates/ui/src/lib.rs:343-356`: `Effect::Quit`, `Effect::Screens` are handled in the UI, and
`Effect::Apply`/`Effect::Launch` are peeked to set the refresh rate (`display.refresh`). It is commented.
Fine as is; if more compositor-side effects come (HDR mode, output scale), give them a
`WindowCommand`-like sub-enum so the split is explicit.

### 1.6 Error handling (verified)
No panics by lint; effects that fail only log (`handles.rs`), and the state is designed so that a failed
effect is harmless (an adopt that fails never promotes because `follow_units` waits for systemd's list;
a Freeze that fails just leaves the slice running). That is the right policy. Inconsistencies: file ops
use `Result<String, String>` strings as the user-facing message (files.rs), `command::run` returns
`bool`, each service has its own `Error` enum. Small: keep as is; the strings are the UI text, which is
reasonable here.

### 1.7 Persistence (verified)
`store.rs`: WAL, every saveable thing written whole in a transaction; `Save::Settings(self.settings.clone())`
on every tile tap. Fine at this size. Two things: (a) `files.rs:258 known_videos` opens a new `Store` per
folder listing; (b) `Store` is also opened in `main::saved`, `wiring::start`, the rescanner, `known()`
and `meta`. Small: pass one `Arc<Mutex<Store>>`/a store worker, or at least cache the probes map in the
browse thread.

### 1.8 Testing strategy (verified)
Strong for a six-day-old codebase: core is unit-tested through `State::apply` with explicit effect
assertions; `ui` has layout invariants (no overlapping targets, every tab at three sizes) and an
allocation-counting test; snapshots are hash-compared; nested-sway and the VM suite cover sway/systemd
integration. Gaps: (1) nothing exercises `follow_*` ordering (see 1.1); (2) the system crate's services
are only tested live (`#[ignore]`) — the `Service` trait makes a fake-backed test possible for `units`
(feed a fake `list` and signal stream) and `sway::windows::reconcile`; (3) `vm-checks.py` positions are
pixel constants (`ICONS`, `BAR_Y`) that break on any bar change — consider having `clamshell ctl` expose
"tap TARGET" (it already does) and use that instead of coordinates where the check isn't about touch
itself.

## 2. Unify / clean up (ranked)

### 2.1 Four pause mechanisms, one concept (verified)
- `Pauses hidden`: `background.rs:111 follow_background` → `Pauses::follow` → `Effect::Freeze` →
  `units::freeze` (units.rs ~276), which spawns a detached thread per request with a global `REQUESTS`
  ticket map and a 2 s "working without drawing" watch loop.
- `Suspend`: same `Pauses` struct via `hold()` plus a parallel `background.suspended: Vec<Arc<str>>`
  (background.rs:35), with special-casing inside `follow_background` (lines ~130-140).
- Found-frozen-at-start: `Event::Frozen` → `found_frozen` → pushes into both `entries` and `suspended`.
- Runner pause: `runner_pauses: Pauses` + `RunnerCommand(pause/resume)` for Waydroid
  (`follow_runner_pauses`), resumed again in `resume_runner_of` before launch/show.
Plus `thaw()` has to be called before Quit/ForceKill/show in three places (running.rs:504, :520, :151).
Recommendation (medium): one `Pause` state per running entry (`None | Hidden { since } | Frozen { by:
Hidden | Suspend | FoundAtStart }`) and treat "the Android runner" as one more pausable thing with the
same state and a different effect (command instead of Freeze). `thaw` becomes part of the single
transition to "shown/ending". The `units::freeze` thread-per-request with a global map should become a
command on one freezer worker (coalescing by unit, latest wins — `worker::spawn_coalescing` already
exists).

### 2.2 Five ways an entry comes to run (verified)
Launch (`launch_with`), scope found at start (`follow_units`), window by app id (`follow_windows` block
1), stray window (`follow_found_windows`), tray icon (`follow_tray`), browsed-file handoff
(`launch_failed` + `follow_windows` "waiting" block). They agree on the outcome (a `Running` on the dock)
but each has its own matching rules (`desktop:<app id>` lowercase in found.rs:58 and tray.rs:82;
`app_id_of` in running.rs:120; `Instance::key_of` in session.rs).
Recommendation (medium): one `fn entry_for(&self, hint: Hint) -> Option<Game>` where `Hint::{AppId,
TrayId, Scope}` holds the three lookups, and one `fn start_found(&mut self, game, origin)` that pushes
`Running` and emits the common effects (Move, Focus-if-front, FindIcon, Adopt). The six construction
sites collapse to two.

### 2.3 Four channels to tell the user something (verified)
`NoticeKind` under the bar (hardware.rs, 2 s), `Effect::Notify` to mako (only the battery warning,
sys.rs:57), `library.problems` (first one shown at the shelf header, shelf.rs:66), and `log::warn`. A
rescan problem (bad library.json) is only visible in shelf's header; a failed adopt/freeze only in the
journal.
Recommendation (small): route everything user-relevant through `NoticeKind` (make `problems` a notice on
`Event::Library`, and surface the first failure of adopt/end as `NoticeKind::Files`-style text), keep
mako only for "over a game". Consider a notice history (last 5) on the Tools tab so a 2 s notice isn't the
only trace.

### 2.4 `panel.rs` is three things (verified)
`crates/core/src/panel.rs` holds settings resolution (`in_force`, `settings_of`, `background_of`,
`is_games`, `env_of`, `setting_levels`), the editor plumbing (`edit`, `paste`, `save_editor` dispatching
Wi-Fi password, keymap names, file names), and `bottom_dark`. Small: split into `settings_resolve.rs` (or
into settings.rs) and `editor.rs` (the `Editor` type already lives in editor.rs).

### 2.5 Naming: `Game` for every entry (verified)
`clamshell_library::Game` is also an app, a folder, a browsed file, a tool and a runner-less place;
`Library::games`, `State::game()`, `Effect::Launch { game }`, `GameEvent`. The docs and comments say
"entry". `tool: bool` means "an app, not in Recent". Medium (mechanical, wide): rename `Game → Entry`,
`games → entries`, `tool → app`; do it once now while unreleased. Also `Tab` (bottom-screen tabs) vs
`Collection` (shelf tabs) vs sway "tabs": fine, but `Collection` is named "tab" in library.json's
`places` — pick one word in the config docs.

### 2.6 `Dirty` is near-binary (verified)
Most arms return `Dirty::BOTH` or `BOTTOM`; `Id::screen()` (id.rs) says Shelf→BOTH, else BOTTOM. The
granularity isn't buying much; either keep it and stop pretending (`Dirty { top, bottom }` is fine) or go
further (see 4.2). No action needed now.

### 2.7 Dead or vestigial (verified)
- `Setting::Upscale`, `Setting::Fan` are inactive placeholders (`Setting::active`), drawn dimmed —
  consistent with "show everything", keep.
- `Launch::None` doubles as "a group" and "nothing"; `Launch::Tool(String)` is matched by string
  (`"rescan"`, `"refetch"` in handles.rs) — small: an enum.
- `Command::MangohudEnv`, `--library`, `--tray` CLI tools: fine as dev tools; `cli.rs` could list them
  under a `--dev` group in USAGE.
- `worker::Worker::gone` stand-ins: good.
- `status.rs` reads volume by spawning `wpctl` every 5 s (status.rs:14-31) although `mixer` has a watch;
  see 4.3.

## 3. Generalize / extend (ranked by payoff)

### 3.1 The `Service` trait + `Bell` is the right seam for the remaining pollers (small each)
`status` (5 s sleep + `wpctl` fork), `battery` sampling, `frames` are the pollers left. `status` could
become a `Service` that listens to UPower/NetworkManager/PipeWire signals and only reads on change (the
wifi/bluetooth/mixer threads already do this for their tabs). Payoff: fewer idle wakeups, which the doc
shows the user cares about.

### 3.2 One "runner command" slot set, data-driven (verified it's already mostly so)
`RunnerOf { command, enqueue, stop, pause, resume, awake }` is a good generalization: the Android runner
is pure config + a shell script. Extend the same way rather than adding Rust: e.g. `screenshot` (a runner
that knows how to grab its own window), `save-state`/`load-state` for RetroArch (its `--input-ipc`/UDP
command interface) would give "Suspend" semantics that survive reboot for emulators. Keep it as a flat
list of named commands rather than new struct fields (`commands: HashMap<&str, Vec<String>>`) so
library.json stays the only place to touch.

### 3.3 `Instance` naming already keys everything (verified) — use it for art/metadata keys too
`key_of(id)` is used for units, workspaces, sockets and art-cache file names. That is one of the better
decisions here; keep every per-entry on-disk artefact keyed by it (MangoHud configs already are).

### 3.4 Control pipe grammar is a good test/automation API (verified)
`control.rs` tables (`COMMANDS`, `TARGETS`) with a shadowing test. Extend with a `query` direction (a
second FIFO or a Unix socket that answers "what is in front / running / tab") so VM checks stop reading
the journal and pixel positions. Medium.

### 3.5 Bottom-screen window rules → general "placement rules" (inferred)
`bottom_screen.rs` rules are `(owner, app_id, title) → down`. If the "reserved bar" idea from
thor-gameplan.md is tried, the same rule shape can carry "fullscreen on top / tiled under the bar".
Don't build it now; just keep `WindowRule` extensible (an enum target instead of implicit "down").

## 4. Technical advice

### 4.1 Robustness
- Pid reuse: `found.rs` adopts by `w.pids.first()` read from sway's tree, then `launcher::adopt`
  re-reads `/proc/pid/cgroup` on a thread later; `EndProcesses` kills pids from the window list. A pid
  can be reused between reading and acting. Low probability on this device; cheap mitigation: pass the
  window id along and re-resolve the pid via sway just before acting, or compare `/proc/pid/stat` start
  time captured at discovery. Small.
- `units::freeze` holds `APPLYING` while calling D-Bus; a thaw request during a 2 s
  `working_without_drawing` sleep waits for the loop iteration (the `latest` check) — OK, but a stuck
  D-Bus call blocks all freezes. One freezer worker (2.1) fixes this structurally.
- `launcher::play` reports `Ended` even when `wait()` errs ("not followed to its end") — correct given
  `follow_ours` uses units as truth. Good.
- `sway/mod.rs` opens a new IPC connection per command (`carry_out`) — fine, sway restarts are handled;
  note `UNITS_KEPT` cache is cleared wholesale at 256 entries (pid→unit cache); pids are reused, so a
  stale mapping is possible until the clear. Small: key the cache by `(pid, starttime)`.
- Clock stepping sends a synthetic `Tick` from the device thread (device.rs StepClock) and
  `clock_stepped` suppresses idle; good. `Event::Resumed` re-applies settings; good.

### 4.2 Performance / power (device unmeasured — these are the things to measure first)
- Full-screen CPU redraws: top 1920×1080 and bottom 1240×1080 via tiny-skia on every `Dirty`. On the
  Thor the top redraws on every window event and every minute; the bottom every second while
  sysinfo/battery is visible (metrics). Measure a frame's cost on the SM8550's little cores; if >10 ms,
  add per-region damage for the bottom screen (the bar vs the tab body already have separate rects)
  before anything fancier. The `no_alloc` discipline means the cost is pure rasterization.
- `view.rs:825-831` converts RGBA→BGRA per frame; the comment notes sway accepts ABGR8888 — use it when
  the compositor advertises it (small win, 2 MB/frame).
- Idle wakeups (the doc's own measurement): remaining pollers are `status` (5 s + fork), `metrics` (5 s
  hidden), `clock` (1 s), zbus executors. The 1 s tick is also what drives
  `follow_windows`/`follow_background` grace timers; consider a 1 s tick only while something is pending
  (a launch starting, a grace running, a notice shown) and 60 s otherwise — the state already knows when
  it needs the next tick. Medium, measurable payoff on battery while idle in shelf.
- Steam following: `steam_launchers()` scans every `/proc/*/cmdline` every 2 s per Steam game thread
  (launcher.rs). With Waydroid up that's a few hundred files; acceptable, but cache `parents()` once per
  scan.

### 4.3 Security (single-user device; nothing alarming, three things to state in docs)
- Clipboard is written to `$XDG_RUNTIME_DIR/clamshell/clipboard` (0600, tmpfs) and offered back after
  restarts; the KDE password-manager hint is honoured (clipboard.rs). Secrets copied from a terminal or a
  game chat are persisted until reboot. Document it; optionally clear on `Event::Quit`/sleep.
- The control FIFO (0600) lets any process of the user inject taps and `type TEXT` into the focused
  window via the virtual keyboard. Waydroid apps run as other uids inside the container, so they can't
  reach it; the `pyclip` stand-in only reaches `--clipboard`. Fine; note in control.rs's doc.
- ratarmount on user archives: Python archive parsers running as the user, in their own scope, indexes
  under cache. OK. Malformed archives are the realistic risk (hangs); the scope + lazy unmount handles
  that.
- The Wayland filter parses untrusted client bytes by hand; `unsafe` is denied so the worst case is a
  desynced proxy connection. Fine.
- Adoption moves processes between cgroups and later SIGKILLs the slice; only the user's own processes
  can be attached (user manager), so no privilege question.

### 4.4 Maintainability
- The codebase's comment style (one paragraph per module, parenthetical asides) is consistent and the
  docs match the code; keep the rule that every "after any change" rule gets a test in the module it
  lives in (running.rs/background.rs do this well).
- Biggest modules: core/lib.rs 1230, pad/remap 1111, running.rs 890, meta.rs 859, system/files.rs 828,
  library/content.rs 829. Only lib.rs is a problem (1.1); the others are cohesive.
- Keymap subsystem (keymap + keymap_screens + ui/views/keymaps + pad/remap/route/motion) is 9.3k lines,
  ~19 % of the code, with its own undo, layers, gyro model and a drawn controller. It is complete and
  tested, but it is the one subsystem whose value depends entirely on device facts still unverified
  (back buttons, gyro source, Home key routing — all listed as open in thor-gameplan.md). Freeze it until
  the device confirms the inputs.

### 4.5 Dependencies
- zbus 5 (+ its async stack) is the heaviest dependency and the source of the executor wakeups; it is
  used blocking everywhere. Alternatives (`rustbus`, hand-rolled) aren't worth it now; consolidating to
  one connection (1.4) captures most of the cost.
- `jiff` in both ui and system, `image`+`resvg` in ui, `rusqlite` bundled? (check `Cargo.lock` for
  `libsqlite3-sys` features; linking the system SQLite on Arch ARM avoids a C build). 211 packages in the
  graph is moderate; `cargo tree -d` would show duplicates worth pinning.
- External programs at runtime (verified by grep): systemd-run, systemctl, udisksctl, bsdtar,
  fusermount3, ratarmount, grim, wpctl, timedatectl, curl, fc-match, nice, timeout, kill, adb, waydroid,
  busctl. List them in one place (`tools/device` package list) and have the Tools tab report which are
  missing (runners already do this for their programs).

## 5. Product advice

### 5.1 What is over-built relative to "simple over complete" (flag, not necessarily cut)
- Files tab: browse + open is the handheld use case (a ROM on an SD card). Copy/cut/paste with progress,
  Trash with freedesktop records and per-filesystem `.Trash-uid`, Restore, Delete-with-confirm, Empty
  Trash, Rename, New folder, Extract-with-progress, archives mounted via FUSE, multi-select — about 1.8k
  lines (core/files.rs, system/files.rs, archives.rs, library browse parts) plus docs. I'd keep
  browse/open/eject/Open-in and freeze the rest unless real use asks for it. The design doc already lists
  "removable filesystems' own Trash" as not done — don't.
- Dock long-press menu has nine items (Open another, Close window, Menu, Pin, Autostart, Move,
  Suspend/Resume, Quit, Force kill). On a 3.9" screen that is a list, not a menu. Close window vs Quit,
  and Suspend vs "Pauses hidden" overlap. Suggest: Pin, Quit, Force kill always; Menu only with a tray
  icon; Suspend/Autostart/Move/Open another behind a second page or dropped (Move can be a drag; Open
  another is rare).
- Settings: 17 tiles, two of them inactive, plus levels All/runner/item and a keymap picker with
  layers/actuations/undo. Fine for an enthusiast; make sure the defaults mean nobody must open it.

### 5.2 Under-built / rough edges a user would hit (verified from code paths)
- Feedback on failure: a launch that fails (`LaunchFailed`) produces no notice (running.rs:287 only
  adjusts state); a Steam game that never starts within 120 s silently ends. Add
  `NoticeKind::Launch(Err(..))`. Small.
- First run: with no library the demo library is shown (main.rs `load_library`), which is good for
  screenshots but on the device the starter library.json exists and may be empty of ROMs — the Games tab
  then has nine empty folders. Hide empty declared folders or show "Put ROMs in ~/Games/snes" as the
  folder's summary. Small.
- `library.problems` only shows the first problem in shelf's header; after a rescan the rest are
  invisible (2.3).
- Idle/sleep while a Steam download or an rsync runs: idle counts input only; the device will suspend
  mid-download (device_session). Consider "no sleep while any entry works" (CPU above a threshold is
  already measured for freezing) or at least while an `Origin::Ours` entry is starting. Medium, worth it
  on a device that hibernates.
- Battery: the tab shows charge history and spenders but no time-remaining estimate or power draw at a
  glance in the bar (metrics has `power`). Small.
- Android: the first app launch takes 12–20 s with no progress shown beyond the dock tile; a notice
  "Starting Android…" when the runner's session isn't running would help. Small.
- Bluetooth pairing of a controller while ClamShell has grabbed the first gamepad: the new controller
  becomes the pad only if `CLAMSHELL_GAMEPAD` matches — check this flow on the device (gameplan lists
  it).

### 5.3 What to add (small, high value)
- Quick resume from the top screen: the dock lives on the bottom screen; a "running" strip or badge on
  shelf's entries for running ones (there is a dot for the program in force on the dock) so Home → shelf
  shows what is paused. Small.
- Play time and "last played" on the details pane (the data is there: `Plays`).
- A one-line system status on the Tools tab: missing programs (5.1 list), library problems, last rescan,
  DB path. Small, and it absorbs 2.3.

### 5.4 Keep
- Process control via scopes/slices + freezing, with "Pauses games" as the default: this is the feature
  that makes the device feel like a console; the design is sound and the VM checks cover it.
- The bottom screen as a shared surface for dual-screen emulators and the Home-chord window moves.
- `library.json` as the single declarative source (places/runners/sources) with "nothing not declared":
  right call; keep resisting per-game config files.
