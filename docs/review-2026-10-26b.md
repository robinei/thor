# Second review and plan, 2026-10-26: after the first review's plan was carried out

Six read-only reviews, run after `history/review-2026-10-26.md`'s plan was done (commit d33ff26):

- (1) the failure handling and effects just changed;
- (2) the window model and Phase 5's moves;
- (3) the shared state;
- (4) organisation;
- (5) test depth, with mutation runs (66 on the state crate, 25 on the compositor and system);
- (6) architecture, runtime and security.

Findings marked *reproduced* were shown by a test in a scratch copy, and those marked *confirmed* were
checked in the code while this was written. Each step of the plan ends in commits that pass
`tools/check.sh`.

## Findings in short

- **Security.** A privilege escalation on a fresh image (*confirmed*). The polkit rule lets the active
  session run `thor-account` without a prompt, and `thor-account password` sets a password unchecked
  while none is set. The image ships `thor` in `wheel` (`%wheel ALL`) with no password. So until the
  user sets one, any process running as `thor` (a Proton game, a Waydroid app) can choose a password
  and use sudo. Besides that, `ext_data_control` is open to every client, so any program can watch
  and replace the clipboard. That was a deliberate revert, but it is written down nowhere, and
  `history/review-2026-10-26.md` still ticks it as restricted.
- **Bugs, by what the user sees.**
  - **The low-battery warning reaches nobody.** It is sent to a notification daemon (mako) that the
    packages no longer have.
  - **Screens come back from dimming darker each time** (*reproduced*). Until ClamShell has set a
    level, a backlight reading taken while dimmed becomes the level: 60, then 20, and so on down to 1.
  - **The global refresh rate is never applied at start** (*reproduced*). `Sent::new` takes it as
    already sent, but the compositor starts at the screen's own rate.
  - **The refresh rate can stay pinned to an app that isn't in front** (today's change). Launch an
    app whose windows go below, or one with no window, while a game is in front.
  - **An app found by its windows that replaces its only window ends and starts again**
    (*reproduced*; a Waydroid cold start). The `WindowBatch` doc claims this can't happen.
  - **A panic in the pad's main loop leaves held keys pressed in the game and the controller dead
    for up to 30 s.** The supervisor catches it before the restart path sees it, skips the pad's
    cleanup, waits out `retry`, and never tells the state.
  - **The pad stops reporting activity after any reconnect** (older bug).
  - **A late launch failure can cancel a newer launch of the same entry.** It names the entry, not
    the instance.
  - **Nothing handles SIGTERM, so the save on quit never runs on the device.** That loses the
    resume save, a debounced brightness and a play being recorded.
  - **Bluetooth's busy mark can stay for good.** That happens after a restart of its connecting
    thread, and a Wi-Fi attempt that fails twice with the same error is never answered either.
  - **A restart of the system thread can put the device back to sleep after the user woke it.**
  - **A lost page flip leaves that screen dead.** The watchdog doesn't see it.
  - **dmabuf imports stall while both screens are off.**
  - **Brightness can be set at full while dimmed.**
  - **A late `KeptAwake` wakes the screens.**
- **The compositor's thread can still block or overwork.**
  - Each client's `/proc/<pid>/environ` is read on it. That takes the target's mmap lock, so a game
    stuck on a FUSE archive can freeze the session until the watchdog fires.
  - The histogram's readback is mapped without a fence, so it can still wait on the GPU.
  - Compose runs on every commit, even while a flip is pending: about 2.5 times the GPU work for an
    uncapped 300 fps game on a 120 Hz screen.
  - D-Bus calls and the library load happen on it at start.
  - The soft fd limit is 1024.
  - One mutex is held across every systemd call, so a slow freeze holds up launches.
- **Restarts are not complete.**
  - Not restarted: the control pipe, the metadata fetchers (whose death also stalls the fetch
    queue), Waydroid's relays, and the UI's font and image threads. The UI's threads also inherit
    the raised priority.
  - A restart whose resend reproduces the panic repeats every 5 s forever.
  - `Thread::WaylandFilter` can't be reached, because the filter is a separate process.
- **State design.**
  - Brightness is desired outside state but isn't in `Wanted`; it is pushed from four places, the
    cause of the dimming bug.
  - `Sent::new` assumes what the outside starts with, the cause of the refresh bug, and `Sent.ui_up`
    is a fact of the state.
  - A rule scans its own output for `Effect::Launch`.
  - Smaller boundary points:
    - `adopt_runner_keymaps` writes `Prefs` directly;
    - `Session::launch` takes the whole shelf in order to save resume;
    - `front_launch` and its deadline are kept in step by hand;
    - three functions return `Vec`.
  - Hot paths allocate: once per event while a launch waits for its unit, and twice per brightness
    slide step.
  - An older placement gap: when a window on the bottom screen opens a dialog, the parent goes to
    the top screen and stays there after the dialog closes.
- **Tests.** The state crate is strongly tested: 93% line coverage, exact effects, settle order
  pinned. But mutations survive in several places:
  - **orders and edge transitions:**
    - keymap before route, and Sleep after Outputs, are not pinned;
    - "a running refresh calibration keeps idle awake";
    - Home+Start on a screen dark for a game;
    - ForceKill thawing a paused entry (the test helpers skip settle and sync);
    - a dialog's close bringing back its parent;
  - **restart recovery:** only the mixer's resend is tested, and nothing tests the `Restarted` event
    end to end;
  - **the device loop:** `drm.rs` `step()` itself, and the X11 serial pairing through the window
    manager;
  - **the pad router:** Home with the D-pad, stick centring, the activity threshold;
  - **failure paths:** the clipboard keeper, corrupt store files, the Steam VDF parser, desktop
    files and D-Bus property maps.

  Two Phase 6 claims don't hold: there is no test of "a capped window's commit let go at once", and
  none of "which screen an input device is on". The fuzz model doesn't generate:
  - files, `Frozen`, `Meta`, `Told`, `XwaylandModes` and `Quit`;
  - tray icons with a unit, or windows closing and reopening.

  Its refresh check copies the code's own formula, so it can't catch a wrong refresh rate.
- **Organisation.** The crate graph, the system crate and the UI's layers are right. What's left:
  - **The environment is read outside `Env`/`Paths` in a dozen places.** The runtime folder is
    built four times.
  - **State areas sit in folders that don't own them.** `device/` mixes the Device view, idle, the
    hardware keys, the sticks, the account and the display modes, and `session/presentation.rs`
    holds a State area.
  - **Overloaded words:**
    - device (seven meanings);
    - profile;
    - session;
    - `Instance` (a launch's unit, with five names in all);
    - trace;
    - Config;
    - two `detached` functions.
  - **Three side channels bypass the cycle undocumented:** `identify`, the screenshot's pixels, and
    the touch layout's shared mutex.
  - **Other leftovers:**
    - `Server` still has about 50 flat fields;
    - the compositor's module docs are one-liners, some stale;
    - the UI ships dev-only code;
    - test helpers are rebuilt in each crate;
    - `remap/mod.rs` (1165 lines) mixes code tables, actuation and analog maths.
- **Docs.** There is no index, and eight finished plans and reviews read as current. About half of
  `state-machines.md` is change notes, partly false now. The overview appears three times and the
  rules four, and the counts in `architecture.md` are stale.

What holds (the reviews checked these and found them sound):
- the boundaries between areas, determinism, and the apply cycle;
- every effect and event has a producer and a consumer;
- waits are bounded;
- the X11 transport never blocks;
- store writes are atomic;
- launches as services, the watchdog and the notifier;
- frame-pacing decisions are pure and tested;
- the restart ordering and backoff;
- today's launch environment and effect group match the old behaviour;
- the window model and Phase 5's moves preserved behaviour.

## Plan

### Phase 1: security

- [x] The first password can't be set by just any process running as `thor`: `thor-account` sets a
      first password only after a hardware key press it reads itself (decision 1).
- [x] The clipboard: `ext_data_control` open to every client is written down as a decision in
      `docs/security.md` (why, what it exposes), with the stale path there fixed. Correct
      `history/review-2026-10-26.md`'s tick.
- [x] Tray icons: `IconName` and `IconThemePath` from the bus are kept to file names under icon folders
      (no absolute paths or `..`); usvg doesn't resolve images from disk.

### Phase 2: bugs

- [x] Notifications: ClamShell is the session's notification daemon and draws notifications itself,
      over the bottom screen (decision 5). The battery warnings become ClamShell's own notifications;
      `Effect::Notify`, `errands`' Notify and the client in `session/notify.rs` go.
      - **System:** a thread owns `org.freedesktop.Notifications` on the session bus. It answers
        `Notify` (with `replaces_id`), `CloseNotification`, `GetCapabilities` (`body`, `actions`) and
        `GetServerInformation`, and emits `NotificationClosed` and `ActionInvoked`. If the name is
        taken, that is logged as a warning and the thread keeps trying.
      - **State:** a `notifications` area holds them by id (app, summary, plain-text body, urgency,
        default action), newest first.
        - Expiry: the timeout follows the request (-1 means 5 s; 0 and critical mean never).
        - Events: `Notified` and `Closed`.
        - Effects: `NotificationClosed { id, reason }` and `ActionInvoked { id, key }`.
        - Idle and power: a critical notification wakes the screens, and turns the bottom screen on
          if it was off by hand or dark for a game. Ordinary ones wait until it is on again.
        - Tests: the state machine in `docs/state-machines.md` with tests, and the fuzz model.
      - **UI:** a recorded overlay layer on the bottom screen, like the top screen's. It is drawn over
        ClamShell's view or the window below. A tap invokes the default action and dismisses; a tap
        on the close mark only dismisses. The screen being off doesn't drop a notification.
      - **Kept simple:** no images, markup stripped, at most a few shown with a count of the rest, and
        no history view.
- [x] Brightness in `Wanted`: the level and shares, dimmed by the idle stage. It is pushed from one
      place, a reading taken while dimmed is ignored, and the restart and Start pushes go (fixes the
      dimming decay and full brightness while dimmed).
- [x] `Sent::new` takes as sent only what the outside starts with: refresh 0, keymap and route
      unsent. `Resend::Start` goes, and `ui_up` moves to `Wanted`. The fuzz model starts the same way.
- [x] `refresh_launch` held only while the entry is launching, or running with no window yet.
- [x] Supervised services after a panic: `lost()` called, the pad's held outputs let go (`router.lose`,
      rumble stopped, `devices.rest()`), reconnected at once, and the state told (`Restarted`).
- [x] The pad's activity watch handed to every new router.
- [x] An entry found by its windows ends only after a grace (`REOPEN_SECS`) without one;
      `WindowBatch`'s doc corrected or the event removed.
- [x] `LaunchEvent::LaunchFailed` carries the instance.
- [x] SIGTERM and SIGINT handled by a calloop signal source: `Event::Quit`, the state's quit runs, the
      store writer is joined, then exit within the stop timeout.
- [x] Bluetooth's and Wi-Fi's busy marks end on a restart and on a repeated identical error.
- [x] Sleep after a restart asked again only if no wake came since it was asked (a generation the
      thread checks).
- [x] A flip that doesn't complete in time clears `pending`, logs a warning, and redraws.
- [x] dmabuf imports completed while both screens are off.
- [x] `KeptAwake` counts as input only while awake.

### Phase 3: the compositor's thread and restarts

- [x] `identify` off the compositor's thread: a client is admitted once its process is identified, on a
      thread per process, its requests waiting in its socket meanwhile (admitted as unknown, it could
      bind the second output, whose global a game's client no longer sees once known). An X11 window
      waits for its process as for its other first answers. The cgroup alone isn't enough: a Steam game
      is told apart by `SteamAppId` in its environment.
- [x] The histogram's readback after a fence signals (zero-timeout check).
- [x] Compose only when a screen can show it: not while every commit since the last compose is a
      window's on a screen with a flip pending; those are composed once at the flip. ("Some screen has no
      flip pending" would compose every commit, the second screen being mostly idle.) Nested composes once a host frame
      already.
- [x] Startup: the environment export and rtkit off the thread; the library loaded once, on a thread,
      by the rescan path.
- [x] `LimitNOFILE` raised in `clamshell.service` (and the soft limit raised at start).
- [x] The systemd calls don't share one mutex across a slow `FreezeUnit`: a connection per caller or
      the freezer on its own.
- [x] Remaining long-lived threads restarted:
      - the control pipe, with its line length limited;
      - each metadata item under `or_on_panic`, so the count stays right;
      - Waydroid's relays ending both sides;
      - the UI's font and image threads through one helper that starts at ordinary priority (the
        compositor's trace and reaper threads too);
      - the freezer in `Handles`.
- [x] Restart storms: after a few panics soon after a restart with its resend, give up on that thread,
      logged at error. `Thread::WaylandFilter` goes.
- [x] Debug-only drops that change what the user gets, raised to warn:
      - an on-screen key with no keycode;
      - an image thread gone (once, not every frame);
      - the freezer's unread cgroup;
      - a tray item unread;
      - an X11 paste refused.

      `bsdtar` and `fc-match` get time limits.

### Phase 4: the state's design

- [x] `Session::launch` returns whether it launched; `launching.rs` stops scanning its effects. The
      resume save moves to State.
- [x] `adopt_runner_keymaps` queues the settings change as an event.
- [x] `front_launch` one `Option` with its deadline.
- [x] No `Vec` returned (`save_effects`, `profile_order`, `cap_env`).
- [x] No allocation while a launch waits for its unit, or on a brightness slide; the no-alloc test
      gets those rows, Idle, a dimmed stage, a window below, and a tray item.
- [x] The dialog of a window below shows on the top screen while its parent stays below (decision 3).
- [x] `setting_slider` with the settings panel.

### Phase 5: tests

- [x] The orders and edges mutation found unpinned: keymap before route in one event, Sleep after
      Outputs, a running refresh calibration keeping idle awake, Home+Start on a screen dark for a
      game, ForceKill thawing a paused entry, the runner's stop once, a dialog's close bringing back
      its parent, `Down` moving keyboard focus, `Changed` keeping `x11`. Each test with a why.
- [x] `testkit`'s `quit`, `force_kill` and `show` go through `apply`.
- [x] Restart recovery: each thread's arm tested (Tuning, Wifi, Bluetooth, Battery, Metrics, Status,
      Account, dimmed Brightness), and the `Restarted` event end to end through `os::worker`.
- [x] The device loop: `step()`'s remaining decisions (commits let through, screen back on dirty, the
      nearest mode) as pure functions with tests; input device → screen as a function with tests; the
      capped window's commit let go at once; the X11 pairing through `pair_surfaces` with the serial's
      halves.
- [x] The pad router: Home with the D-pad, stick centring outside a game, the activity threshold, Home
      in `resync`. The pad supervisor's reconnect with a fake device was left: it needs uinput devices; the
      supervisor's panic path is tested with a test service (`os::worker`).
- [x] Failure paths:
      - the clipboard keeper (size limit, non-UTF-8, password managers);
      - corrupt store files;
      - the Steam VDF parser (depth bound);
      - malformed desktop files;
      - D-Bus property maps parsed in-process (BlueZ: check `hci1` vs `hci10`).
- [x] The fuzz model:
      - **generates:** files events, `Frozen`, `Meta`, `Told`, `XwaylandModes`, `Quit`, tray icons
        with a unit, and a program's window closed and reopened;
      - **follows:** `Adopt`;
      - **new invariants:** the tab watches exact, Freeze equal to paused, brightness sent equals the
        level dimmed, every window placed after settle, at most one selection per group;
      - **refresh check:** worked out independently of the code's formula. Left: the rule is the
        specification, and its cases are pinned by unit tests; `Frozen` is drawn only at a start in
        reality, so it isn't drawn mid-run.
- [x] Compositor tests share one `Server` builder and one client loop helper.
- [x] The long multi-behaviour compositor tests split (after Phase 3's compositor work).

- [x] State areas in folders they own:
      - the Device view `setup` (`Setup`; the view keeps its name in the UI and its ids);
      - idle on its own;
      - the hardware keys with `keys.rs`;
      - the display modes a reading kept by `Presentation`;
      - `presentation/` at the root;
      - the `impl State` files under one folder (`apply/`);
      - the unused `Instance::order` and `Rotation::degrees` go. Left: `Init::display_modes`, which the
        snapshots' state starts from (a reading there would move the first effects in the trace).
- [x] Names (decision 4): `Instance` → `LaunchUnit`;
      `DeviceKey` → `HardwareKey`; the device `Profile` → `DeviceProfile`; the panel's `Scope` →

- [x] The side channels documented in `architecture.md`. The touch layout went into the cycle after

- [x] `remap/mod.rs` split (codes, actuation, analog); `Server`'s pointer and screen fields grouped;

- [x] A `dev` feature on clamshell-ui for the snapshot and pad-view code. The `testkit` feature was

### Decisions (taken 2026-10-26)

1. **The first password:** a physical key press. The root helper reads a hardware key from evdev
   itself before it sets a first password, which no ordinary process can fake.
2. **The clipboard:** stays open to every client; `docs/security.md` says what that exposes and why.
3. **A dialog of the window below:** shows on the top screen while its parent stays on the bottom one.
4. **Renames:** all of Phase 6's, with the state's folder moves.
5. **Notifications:** ClamShell serves `org.freedesktop.Notifications` and draws notifications over the
   bottom screen.
