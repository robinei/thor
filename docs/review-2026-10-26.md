# Review and plan, 2026-10-26: after the compositor became the only session

Six read-only reviews of the code after sway and uwsm were removed and launches became transient services:
the shared state and its operations, organisation, tests, the architecture principles, one program or
several, and everything else (leftovers, the hot path, untrusted input, dependencies, packaging). The
claims marked *confirmed* were checked in the code before this plan was written. Each step below ends in
one or more commits that pass `tools/check.sh`; the VM suite runs at the end of a phase that changes the
session, input or launches.

## Findings in short

- **State.** The boundary is right: events in, effects out, the state pure, placement during `apply`,
  only closing a window an effect. The data behind it is still shaped by sway: a group is a string
  (`"clamshell-run-<key>"`, `Window.workspace`) parsed back for its owner; `Window` holds both what the
  compositor knows and where the state placed it, and the compositor computes `focused` for `Opened`
  itself (`opening_focus`, server.rs, x11/wm.rs); who is shown is held in overlapping flags and lists
  (`focused`, `visible`, `selected`, `recent`, `followed_front`, `closed_front`) and the bottom screen,
  one slot, as flags on every window; placement is spread over `State::window_event`, settle steps,
  `Bottom` (with all of `&mut Session`) and `Device`. The settle order in its doc is out of date.
  `Event::Paste` lost its producer with the UI's client (*confirmed*: right-click paste on the second
  screen is gone); `Event::Quit` has none (*confirmed*: the save on quit never runs).
- **Organisation.** The crate graph points the right way and the binary is thin. Leftover names: scope
  where launches are services, workspace for groups, `Instance::Shelf` used only by tests. `server.rs`
  (about 60 fields, eight concerns) and the state's `lib.rs` (1634 lines) are worth splitting;
  `session/presentation.rs` is a grab-bag (window presentation, the colour model, curve plots); tests
  follow three layouts; the HUD and window arrows are drawn outside the UI's core; the screenshot's
  pixels are one struct under three names; public surface wider than used.
- **Tests.** 789 tests; the state, the UI and the protocol-facing compositor are well tested. Today's
  frame pacing has none: `drm.rs` `step()` (present, callbacks, wake), FIFO barriers, commit timing,
  latching, the xwayland_shell pairing, the notifier. Two tests start real units on the machine running
  the checks. The VM's touchpad checks enable tapping in their own libinput context, so they don't test
  the compositor's. `capture()` in the VM checks matches its own command line (*confirmed*: about 3 s lost
  per capture).
- **Principles.** Mostly kept. Broken: the compositor decides a window's opening focus and rewrites
  `Effect::Launch` on its way (the launch's environment is put together in three places); nested keeps a
  second drawing path the device never runs; the HUD and arrows bypass the core's recording; some
  fallbacks unlogged (credentials, DRM encoder/CRTC queries, an abstract notify socket); a freezer thread
  outside `os::worker`; blocking work on the compositor thread (`/proc` walks per client, a GPU readback
  for the histogram, `end_processes`/`runner_command`). The wording of "no panics", "unsafe denied",
  "no silent failures", "one place per effect" and the threading rule needs restating for a compositor.
- **One program or several.** More boon than bust: placement before first show, input in one hop, no
  buffer protocol, about 40 MB resident; the risky parsers are already in other processes or on threads.
  Risks: a panicking system thread dies for good, unseen (no panic hook; panics reach the journal at info);
  the UI's CPU drawing shares the compositor thread, with whole redraws from the hidden top screen being
  drawn and from the burn-in drift.
- **Everything else.** rtkit's nice level reaches every system thread, since threads inherit it
  (*confirmed*). `sync_windows` and the per-frame paths scan the library linearly per window several
  times a frame. The device loop spins while a frame is queued and a held callback is due (*confirmed*,
  drm.rs). Stale comments promise launches survive a restart; children inherit `NOTIFY_SOCKET`; any
  client can read the clipboard (`ext_data_control`); curl downloads have no size limit; the VM's package
  list drifted from the session's; the slices thor-session stops have no unit files (it fails noisily
  when they never ran).

## Plan

### Phase 1: bugs and failure handling

- [x] The device loop doesn't spin while a frame is queued: a held callback's time counts toward the
      wake only when it can be sent (drm.rs `step`).
- [x] rtkit's nice level only for the compositor thread: system threads (`os::worker`) reset their own
      nice as they start; the raise documented accordingly.
- [x] Right-click on the second screen pastes again (the compositor sends `Event::Paste`); the
      compositor quits through `Event::Quit`, so the state's quit (its saves) runs.
- [x] A panic is logged at error with its thread and place (a panic hook); a supervised system thread
      that panics is restarted as one that lost its connection is; one that can't be is logged.
- [x] The window's open line logs the focus it opens with.
- [x] Logged fallbacks: the client credentials lookup, the GPU and DRM encoder/CRTC queries, an abstract
      `NOTIFY_SOCKET`, a stale X11 lock that can't be removed.
- [x] Only ClamShell's own clipboard thread may use `ext_data_control`.
- [x] curl's downloads have a size limit.
- [x] thor-session stops the slices quietly when they never ran; the comments that promise launches
      survive a restart say what happens.
- [x] The VM's packages match the session's (udiskie, the GTK portal, dbus); `capture()` in the VM checks
      waits on an anchored `pgrep`.

### Phase 1b: every thread restarted after a panic, and what it lost recovered

A panic in a system thread ended it for good, except the supervised services (the pad, Wi-Fi, Bluetooth,
the tray), which reconnect. Every long-lived thread is restarted now, and tells the state, which sends
again whatever the thread may have lost. What can't be recovered, and needn't be, is said so.

- [x] Every worker (`Worker::spawn`, `spawn_belled`) and long-lived thread (`worker::lasting`: the clock,
      input watching, the units, the clipboard keeper, sleep's hold, the freezer, the pad's device watch,
      Waydroid's filter; the store writer) runs its body again after a panic, on the same channel: at
      once, then after waits doubling from 250 ms to 5 s while it keeps panicking within 30 s of starting.
      The wiring sends `Event::Restarted(Thread)`; threads are named by `clamshell_state::Thread`, so a
      name can't drift. Supervised services keep their struct, so the pad keeps a game's virtual
      controller. Short-lived threads aren't restarted; those the state waits on answer with a failure
      if they panic (`worker::or_on_panic`: a launch, the refresh calibration, an account change).
- [x] The state's recovery, per thread (`state/src/restart.rs`, with tests):
      - the pad: its keymap, route, activity watch and the settings applied (the rumble) sent again;
      - tuning: the settings in force applied again;
      - the mixer, battery, metrics, status, Wi-Fi, Bluetooth: the watches sent again (the open tab's,
        the bar's status, the account), so their readings come again;
      - brightness: the level sent again, dimmed if idle has dimmed it;
      - the store writer: everything the state saves written again; a play being recorded is lost;
      - the system thread: the watches again (it reads the time and the account as their views open),
        and sleep asked again if it was asked last; a screenshot or notification in flight is lost;
      - files: the operation in flight ends as failed; those queued behind it run;
      - browse: the folder open listed and watched again, the files in use sent again;
      - icons: the icons of entries found by their windows asked again;
      - the freezer: every slice of ours frozen or thawed again as it is paused or not;
      - the launcher: nothing (each launch is its own thread); a video's position read is lost;
      - Bluetooth's connecting thread: the connection under way ends, shown as not busy;
      - the units, the touchpad, sound, the clock, input watching, the clipboard (its saved text is
        offered again), sleep's hold, the tray, Waydroid's filter: nothing the state sent stands.

### Phase 1c: panics avoided where they can be

Both angles: the restarts (1b) are the backstop for what can't be avoided (a dependency's panic, a mistake
not yet seen); what our code can avoid, it does. Clippy already denies `unwrap`, `expect`, `panic!` and
indexing outside tests; these panic without those:

- [x] Lints denied too: `unreachable`, `todo`, `unimplemented`, `unchecked_time_subtraction`
      (`Instant - Duration` panics before the clock's start, `Duration - Duration` below zero). The
      guarded subtractions became saturating so the lint sees them; `x11/shell.rs` logs an unknown
      request instead of `unreachable!()`.
- [x] `copy_from_slice` and `split_at`: every one copies between lengths equal by construction (fixed
      arrays, `get_mut` ranges of the same length, a split at a found index); left as they are.
- [x] `Duration::from_secs_f64` in `nested.rs`: always a finite positive value (a rate at least 1000
      mHz); left.
- [x] Integer division and remainder (clippy's `integer_division` listing, 69): one divisor could be
      zero, the nested preview's width split, now guarded. The rest divide by constants or by values
      checked or clamped just before.
- [x] `RefCell` borrows: each is taken in a callback of its own or after the state's events are applied,
      none re-entered. The production `assert!`s are a compile-time check and a test-only module.

### Phase 2: the compositor thread's work per frame

- [x] A window's presentation, fill size, frame cap, curve and clarity computed once per state revision,
      not by library scans per frame (`sync_windows`, `frame_callbacks`, `release_timed_commits`,
      `compose`); the library's entries found by id without a scan.
- [x] The top screen isn't drawn while a window covers it, and is drawn whole when uncovered.
- [x] Small: an input device's identifier kept from when it is added (no `format!` per event); no compose
      while both screens are off; the colour chain's failed surfaces pruned; no `Vec` per drawn element
      for its uniforms.
- [x] The histogram's readback a turn later, so the compositor's thread doesn't wait for the GPU.
- [x] Found on the way: a launch has ClamShell's environment again (a service started with the user
      manager's, which sent a test ClamShell's games to another compositor); a game connecting before its
      unit is listed is its entry's (a service's program starts with its unit).

### Phase 3: the window model

- [x] `WindowFacts` (what the compositor knows) for `Opened`/`Changed`, the session's own record for
      placement; the state decides the opening focus itself (no `opening_focus` call from the
      compositor or the X11 window manager).
- [x] A group is a typed value (`Group::Entry(key)` / `Group::Window(id)`), `Window.workspace` becomes
      `group`; no parsing of owners out of strings.
- [x] The top screen's window and the bottom screen's slot held once, not as flags on every window.
- [x] Placement in one area that owns group assignment, both screens' windows and the bottom rules;
      `Bottom` keeps its tabs and power and reads the bottom window.
- [x] `Instance::Shelf` and the workspace helpers go; `instance.rs` only names units and slices.
- [x] The settle order's doc matches the code, each ordering constraint next to its test.

### Phase 4: effects and the launch's environment

- [x] A launch's environment put together where each part is known: the cap's FIFO variables by the
      state, the controller's by the system, the displays by the launcher (given them at start).
      `Effect::Launch` passes the compositor unchanged.
- [x] The compositor's own effects in a group of their own, `Effect::Compositor(Compositor::…)`: the
      compositor matches it, the system's dispatcher passes it in one arm. `DumpWindowEvents` is in it.
- [x] The wanted refresh rate a plain value (`Wanted::refresh`): the calibration's, else the entry
      launched last until the program in force changes (`Session::refresh_launch`), else the settings'.
      No scan of sync's own effects, no `Resend::RefreshCalibrated`. A failed launch now gives the screen
      back to the settings' rate, and new display modes send the rate they give.
- [x] `EventSender` in the compositor; the UI crate no longer needs calloop.

### Phase 5: organisation

- [x] Names: `launch/scopes.rs` → `launch/units.rs`, scope → unit where a launch's unit is meant (the
      system, the state, the docs); scope stays for adopted programs.
- [x] `server.rs` split by concern: `windows.rs`, `pacing.rs` (frame callbacks, FIFO, timed commits,
      presentation feedback), `clients.rs`, `protocols.rs`, `x11::Bridge`; `Server::hit` in `input.rs`.
- [x] The state's `lib.rs` (1607 → about 630 lines) split into child files of `impl State` by subject;
      the colour model in `state::colour`, the plots in `curve/plot.rs`; the screens, Xwayland's modes
      and the histogram one area, `session::presentation::Presentation`.
- [x] The HUD and window arrows a recorded layer of the UI's core (`views/overlay.rs`,
      `Layer::Overlay`), with line icons and targets (`Id::WindowArrow`).
- [x] Nested requires the colour pipeline: the fallback drawing path and its screenshot are gone, and a
      pipeline that can't start ends nested with an error.
- [x] One screenshot pixels type, `clamshell_state::ScreenshotPixels`; the system thread's worker is
      `errands.rs`; `pub` narrowed in every crate (unused items found that way removed); the GLSL in
      `colour/shaders.rs`; one test layout (inline while small, `tests.rs` beside the module when large;
      the compositor's protocol tests in `src/tests/`).

### Phase 6: tests

- [x] The device loop's decisions as a pure function, tested: held while queued, the timed commits'
      wake, idle callbacks at most once a refresh; the nearest mode; which screen an input device is on.
- [x] Protocol tests: a FIFO barrier let go only once its frame is shown; a timed commit held and let go;
      a capped window's let go at once.
- [x] xwayland_shell pairing: serial before and after the commit, a reused surface id never paired.
- [x] The notifier against a socket: ready once, the watchdog's cadence, the status deduplicated.
- [x] Tests that start real units are `#[ignore]` with their reason, named for services.
- [x] VM checks (`session_units`): the compositor's own tapping on the touchpad, the environment the
      session exports, the status line. A refresh change is left to the device: the VM's virtio display
      has only 60 Hz at the Thor's size, so there is no change to see; choosing the rate is tested in the
      state and in `drm.rs` (`nearest`).
- [x] The fuzz model sends only facts (Phase 3), opens X11 windows with their roles, and restarts
      threads; 2000 seeds pass.

### Phase 7: principles and docs

- [x] AGENTS.md and docs/architecture.md: no panics by construction, the panic hook, threads started
      again and systemd restarting ClamShell; `unsafe` only for a block at an FFI boundary with a
      `SAFETY:` comment; the compositor's thread doesn't block and draws what changed; a thread per
      concern on a channel; failures that change what the user gets logged above debug; the
      compositor's effects one group, the rest passed on unchanged.
- [x] Docs for every phase's changes (state-machines.md: the restarts, the refresh value, the units);
      the stale mentions in runners.md, process-control.md, device-profiles.md and the unit names.

### Considered and left

- The burn-in drift as a texture offset: the shifted texture needs cropping to its screen, the bar's crop
  where windows below start moves with it, windows below would have to move too, and input would need the
  drift taken off in three places. With the covered top screen no longer drawn, what is left is a whole
  redraw of the second screen about once a minute: measured on the Thor first.
- No `Vec` per drawn element for the colour shader's uniforms: smithay's `override_default_tex_program`
  takes them by value.
- `/proc` walks per client, `end_processes` and `runner_command` on the compositor's thread: once per
  connecting client, or a signal and a `posix_spawn`, each well under a millisecond.
- The clipboard's protocol only for ClamShell's own program (tried, reverted): wl-clipboard and clipboard
  tools use it, as on sway and KDE.

- Children ClamShell starts itself inheriting `NOTIFY_SOCKET`/`WATCHDOG_*`: the service has
  `NotifyAccess=main`, so systemd ignores them, and launches are services with an environment of their
  own; clearing the variables at start needs `std::env::remove_var`, `unsafe` since Rust 2024.

- The clipboard thread and the Waydroid filter as compositor features: they work as clients; moving them
  pays only if it simplifies, which isn't clear now.
- The virtual touchpad through uinput and libinput back into the same process: it keeps libinput's
  acceleration and tapping.
- `panic=abort`: a dead thread would become a dead session.
- Helper processes for parsing, the UI drawn on its own thread, the compositor split from the UI: not
  needed (the parsers are isolated or memory-safe; measure on the Thor after phase 2 first).
- Real-time scheduling for the compositor thread: on the device, measured.
