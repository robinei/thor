# Compositor measurements, 2026-10-31

ClamShell at `80df1b99`, built with the optimised `fast` profile, on a Ryzen 9 5900X and
Radeon RX 9070 XT. Linux 7.2.9-2-cachyos; CPU governor `powersave`, energy preference
`balance_performance`. The GLES renderer reported radeonsi, gfx1201 and ACO.

The compositor ran nested in GPU-backed headless sway at 60 Hz, with a 1920×1080 top
screen and 1240×1080 bottom screen. The Library contained 1,000 generated local ROM
files, plus two built-ins. No apps, Xwayland or metadata fetches ran. Each case used a
private home, runtime directory and session bus through the real-client harness.
The host's systemd user manager and user-bus services were unavailable inside that
fixture. The owner's desktop session remained running. These are desktop nested
measurements; the Thor's DRM, Adreno, suspend and power figures require the device.

## Starting

Each case started once with fresh saved defaults and cache directories, then restarted
ClamShell nine times with the same files and shader cache. Sway and the private bus
were already running when the clock started. The OS page cache was left alone.
The table combines the 18 subsequent launches from the two cases.

| Observation | Median | Range |
|---|---:|---:|
| `READY=1` received | 87 ms | 82–94 ms |
| Both UI screens first composed | 84 ms | 80–91 ms |
| Library scan completed | 79 ms | 76–80 ms |

The two launches with fresh benchmark directories reached readiness in 155 and 163 ms.
These are observations from immediately before spawning the process. Readiness is
received on a private notification socket. Composition and library loading are observed
in logs polled every 2 ms; they do not establish physical presentation latency or when
the populated Library first became visible. Readiness means the loop has turned and
setup has completed, as it does for the session's systemd service.

## No-input running cost

After the final launch, the selected bottom tab settled for ten seconds. Each case then
had three consecutive 30-second samples. Screenshots were checked before sampling:
the Library was shown above, with either Dock or the live System page below.

| Measurement | Library + Dock | Library + System |
|---|---:|---:|
| CPU, percent of one core | 1.57–1.66% | 2.54–2.97% |
| RSS | 132.2 MiB | 132.2 MiB |
| PSS | 83.5 MiB | 83.4 MiB |
| Voluntary context switches per second | 591–612 | 566–634 |
| Threads | 43 | 43 |
| Per-client graphics engine busy time | 3.69–3.75% | 3.61–3.72% |
| Driver-accounted resident VRAM | 125.8 MiB | 125.8 MiB |
| Driver-accounted resident GTT | 11.3–21.8 MiB | 10.3–12.3 MiB |

CPU time is the sum of thread runtime deltas from `/proc/PID/task/TID/schedstat`,
divided by elapsed monotonic time. A busy core is 100%, regardless of the machine's
24 logical CPUs. Sampling rejects thread identities changing between snapshots.

RSS/PSS come from `smaps_rollup`. PSS apportions shared pages, including sharing with
the existing desktop and its ClamShell process. GPU counters come from DRM `fdinfo`,
counted once per device/client ID even when several fds refer to it. Engine busy time
is this client's graphics-engine counter delta. Resident GPU allocations include shared
and reclaimable buffers; GTT can overlap process mappings. These columns cannot simply
be added to PSS to obtain total physical memory consumption. Host sway and the private
bus are excluded from the process measurements.

`kernel.sched_schedstats` was disabled, and privileged tracing was unavailable. The
voluntary context-switch deltas are a wakeup proxy, not scheduler wakeup counts or a
measurement of hardware power states.

The largest thread contributions, averaged over each case's 90 seconds, were:

| Thread | Dock CPU | System CPU | Dock voluntary switches/s | System voluntary switches/s |
|---|---:|---:|---:|---:|
| Main loop | 1.03% | 1.31% | 264 | 254 |
| Metrics | 0.20% | 1.03% | 0.6 | 2.9 |
| Winit event pump | 0.18% | 0.17% | 205 | 200 |
| Mesa command submission | 0.17% | 0.17% | 63 | 65 |
| Mesa graphics driver worker | 0.04% | 0.03% | 63 | 64 |

The nested backend requests another redraw after every host frame and presents through
its colour pipeline even when the UI recording is unchanged. Its frame-driven main,
event-pump and driver work accounts for most context switches in both cases. The System
page adds metrics polling and graph updates. These results establish a nested baseline;
they do not measure the DRM backend's behaviour when no drawing is due.

## CPU drawing

The existing views benchmark warmed its caches for 20 rounds, then reported the median
of 200 rounds at the same screen sizes, using the demo library. It measures CPU UI work,
separately from the compositor's GPU composition and presentation.

| Screen | Record and paint a whole frame | Paint only | Record and compare unchanged |
|---|---:|---:|---:|
| Library | 0.431 ms | 0.406 ms | 0.026 ms |
| Dock | 0.120 ms | 0.116 ms | 0.004 ms |
| Settings | 0.366 ms | 0.339 ms | 0.027 ms |
| Keyboard | 0.252 ms | 0.226 ms | 0.028 ms |

The warmed steady-state allocation checks remain separate correctness tests; these
timing measurements impose no pass/fail thresholds.

## Repeating the measurements

The desktop needs the nested real-client test dependencies and a working hardware GLES
driver. Choose the render node for the GPU to measure; this machine used `/dev/dri/renderD128`.
Each invocation leaves its JSON, compositor log and screenshot beside the output path.

```sh
cargo build --manifest-path clamshell/Cargo.toml --profile fast
tools/measure-session.py --render-node /dev/dri/renderD128 --tab dock --output /tmp/thor-dock.json
tools/measure-session.py --render-node /dev/dri/renderD128 --tab sysinfo --output /tmp/thor-sysinfo.json
cargo test --manifest-path clamshell/Cargo.toml --profile fast -p clamshell-views frame_times -- --ignored --nocapture
```

Raw results: [Dock](2026-10-31-dock.json), [System](2026-10-31-sysinfo.json),
[CPU drawing](2026-10-31-ui-frames.txt). The measurement tool is
[`tools/measure-session.py`](../../tools/measure-session.py).
